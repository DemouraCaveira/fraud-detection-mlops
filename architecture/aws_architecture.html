Da mesma pipeline local para uma arquitetura de produção na AWS

Este desenho leva o pipeline construído em src/ — os mesmos passos de ingestão, pré-processamento, treino, registro e explicabilidade — para um ambiente produtivo real, com ingestão em tempo real, retreino orquestrado e um caminho de inferência medido em milissegundos, não simulado.

Fluxo completo: transação → data lake → treino/registro offline → endpoint em tempo real (destacado em âmbar, o caminho cuja latência foi medida) → captura de inferências → monitoramento de drift → gatilho automático de retreino, fechando o ciclo de volta ao treinamento.

Lane 1Ingestão & Data Lake

Cada transação chega ao Kinesis Data Streams como evento — o mesmo formato que hoje é lido direto do parquet estático em src/ingestion.py, só que contínuo. O Kinesis Firehose persiste tudo em S3 (raw zone) sem transformação, para nunca perder o dado bruto.

O Glue ETL / SageMaker Processing roda exatamente a lógica de src/preprocessing.py (limpeza, features cíclicas de horário, split temporal) containerizada, gravando em S3 curated particionado por data. O SageMaker Feature Store materializa essas features em dois lugares: a store offline (para treino) e a store online (latência de leitura <10ms, para o endpoint de inferência não recalcular features na hora).

Por que essas escolhas
Kinesis em vez de fila tradicional (SQS)
Fraude precisa de múltiplos consumidores do mesmo evento (scoring em tempo real + gravação no data lake) sem competir pela mensagem — é o caso de uso central do Kinesis.
Feature Store com duas camadas
Garante que a feature usada no treino e na inferência seja calculada pelo mesmo código — evita o erro clássico de "training-serving skew".

Lane 2Treinamento & Registro

O SageMaker Training Job roda o mesmo src/train.py — baseline + LightGBM com tuning via Optuna — dentro de um container, em instância Spot (~70% mais barata que on-demand; aceitável aqui porque o job é curto e reprodutível caso a instância seja interrompida). Disparado por EventBridge (agendado) ou pelo alarme de drift do Model Monitor (lane 4).

Antes de virar produção, o modelo passa por um gate de aprovação: só é promovido no SageMaker Model Registry se suas métricas de validação igualarem ou superarem o modelo em produção — o mesmo tipo de checagem que fizemos manualmente no Checkpoint 1 deste projeto, aqui automatizado.

Por que essas escolhas
Spot em vez de on-demand
O treino completo (tuning + fit final) leva ~39s neste projeto — mesmo com alguma interrupção e retry do Spot, o custo total continua desprezível frente ao ganho de ~70% no preço da instância.
Gate de aprovação automático
Sem isso, um retrain automático poderia promover um modelo pior sem ninguém perceber até o impacto aparecer em produção.

Lane 3Serving em tempo real — o caminho medido

Esta é a única parte do diagrama com números medidos, não estimados: o modelo LightGBM treinado neste projeto responde uma predição em p50 = 1,0 ms / p99 = 2,1 ms (deploy/benchmark_latency.py), e sustenta 511 mil predições/s em lote. Isso é o que justifica hospedar o modelo num SageMaker Real-Time Endpoint multi-AZ com auto-scaling — a latência do próprio modelo é uma fração pequena do orçamento total de uma autorização de cartão (tipicamente algumas centenas de ms), sobrando margem confortável para rede, validação e possíveis retries.

O API Gateway + Lambda na frente do endpoint fazem validação de payload e autenticação antes de invocar o modelo — mantendo o endpoint SageMaker dedicado só à inferência.

Alternativas consideradas
Por que não KNN, apesar de ser competitivo em métricas?
O benchmark de complexidade (Fase 3) mostrou latência de KNN crescendo de 2,2ms para 7,5ms conforme o volume de treino cresce (O(n) por predição) — inviável para um endpoint que precisa escalar o dataset de treino ao longo dos anos sem degradar a latência de produção.
Endpoint dedicado vs. Serverless Inference
Para tráfego de autorização de cartão (alto volume, baixa tolerância a cold start), um endpoint sempre ativo com auto-scaling por invocações/instância é mais previsível; Serverless Inference fica reservado para ambientes de menor tráfego (ex.: staging).

Lane 4Monitoramento & Retreino

Toda inferência é capturada (input + output) e comparada, de forma agendada, pelo SageMaker Model Monitor contra a distribuição de referência do treino — a mesma técnica de PSI/KS implementada em monitoring/drift_monitor.py, que já mostrou neste projeto um PSI real de até 7,5 nas features de horário entre treino e teste, e detectou corretamente um choque simulado de +60% em Amount (PSI 0,17, moderado).

Quando o drift ultrapassa o limiar, um CloudWatch Alarm dispara duas coisas em paralelo: um alerta via SNS para o time de risco, e — fechando o ciclo — um retrain automático de volta na Lane 2, sem esperar o próximo agendamento semanal.

Indicadores de acompanhamento
Data drift
PSI/KS por feature, diário, contra o baseline offline do Feature Store.
Concept drift
PR-AUC calculado assim que rótulos de chargeback chegam (com atraso de dias/semanas) — degradação aqui é mais grave que data drift porque significa que o padrão de fraude mudou, não só o tráfego.
Performance operacional
Latência p99 do endpoint e taxa de erro, monitorados continuamente — não semanalmente.
Diagrama construído a partir dos números reais medidos neste projeto (Fases 3–6) — não é uma proposta genérica, é a arquitetura que este pipeline específico assumiria em produção.
